# AGENT 模式（实验性功能）

本文档说明 NarrChat 的 AGENT 模式（「设置 → 通用设置 → 会话工作模式（实验性）」
中的**两档下拉：关 / Agent Lv.1**，默认**关**）：档位与平台接入协议**全解耦**——
协议只决定线路格式（见下文「模式与协议」），档位决定生成流程、上下文构成与工具集。
工具级细节见 `docs/agent_tools.md`。原来的 Agent Lv.2 已从产品移除，
见文末「已移除：Agent Lv.2」。

## 术语：轮 → 步 → 回合

- **轮**：一次用户发送到最终落库的一条 `Round`，是持久化、展示、版本切换的单位；
- **步**：一轮内的两个生成步骤——第一步「调研 + 正文」，第二步「状态维护」；
- **回合**：一次 AI 请求—响应（代码里的 frame / 一次 HTTP 往返），是**最基础的单元**。

一步可以包含多个回合：第一步通常至少是「调研回合 + 正文回合」，联网时更多；
第二步至少一个维护回合，必要时有修复回合。无联网的合规一轮典型为 **3 个回合**。

## 模式与协议（全解耦）

设置 →「API 设置」中每个平台一个**接入协议**——**协议只决定请求体 / 线路
格式**，不决定档位。档位是「设置 → 通用设置 → **会话工作模式（实验性）** →
**Agent 模式**」中的独立下拉：描述中声明会调用的自定义工具（见下表）、两步生成 /
`previous_response_id` 链式续接 / 状态工作副本合并等特性，
以及思考 / 流式 / 搜索在 Agent 期间**强制开启**（可在模型配置页关闭对应能力
以禁用），并明确说明可能导致失败、兼容性与正确性不保证。

| 协议 \\ 档位 | 关（默认） | Lv.1 |
|---|---|---|
| OpenAI Chat API 兼容 | 传统 Chat 对话（6 区块输出 + 可选联网搜索循环），`POST {baseUrl}/chat/completions` | Agent 两步流程在 Chat 通道运行（回合转为 `tool_calls` / `role: tool` 消息；无 `previous_response_id`，每回合全量重发） |
| OpenAI Response API 兼容 | 纯文本单轮（instructions + input，无工具 / 状态机制）；联网搜索为 Responses 工具循环，`POST {baseUrl}/responses` | Agent 两步流程（历史一读一写 + 工作副本；有状态平台可开启链式续接） |

内置默认平台与自定义平台的「API 类型」下拉均可实时切换（保存后立即生效，
无需重建平台）；「自定义请求体模板」功能已移除（未来以独立于兼容的高级
自定义另行设计）。

### 强制开启的语义（不改写用户设置）

Agent 期间 `思考 / 流式 / 搜索` 一律**按模型能力强制为开**（`supportsThinking` /
`supportsStreaming` / `supportsSearch`，由模型配置页控制）：组合时快照覆盖，
**不写入**用户已保存的 Chat 每轮选项；关闭 Agent 后立即恢复用户原设置。
能力不支持时对应功能自然关闭（搜索工具不注入、思考不强制发送）。

## 核心设计：两步流程（正文与状态分开）

旧版把「写正文」和「维护状态字段」塞进同一次响应，模型既要自由写作
又要逐条调工具，稳定性差（正文重复输出、状态漏项）。现在按两步拆开：
**Lv.1 为两步**——第一步「调研 → 正文」，第二步「状态维护」；执行器步骤枚举为
`AgentStage{prepare, story, state}`：

| | 第一步·调研回合 | 第一步·正文回合 | 第二步·维护回合 |
|---|---|---|---|
| 是否必发 | **必发** | 是（调研结束后立刻） | **每轮必发**（正文完成后单独新请求） |
| 回合数上限 | `kAgentMaxPrepFrames` = 6（联网搜索要吃多回合） | `kAgentMaxStoryFrames` = 8（联网搜索要吃多回合） | `kAgentMaxStateFrames` = 4（1 主回合 + 3 修复回合） |
| 文本通道 | **不上屏**（只备事实依据，不写记忆 / 正文） | **唯一正文上屏回合**（门控后上屏，开场白不可见） | **只进维护流式框**（绝不进入正文） |
| `max_output_tokens` | 用户设置值 | 用户设置值 | **程序不擅改**：未启用子模型时同主模型；启用时用子模型自己的配置 |
| 思考（reasoning） | 用户设置值（Agent 期间强制开启） | 用户设置值（Agent 期间强制开启） | **程序不擅改**：默认同主模型；启用子模型时按子模型能力与默认强度 |

工具调用由**回合指令 + 工具描述**驱动（每回合明确要求本回合直接调用对应编辑器），
**不发送 `tool_choice`**：部分服务商在思考模式下以 400 拒绝该参数
（`Thinking mode does not support this tool_choice`），而步骤语义并不依赖它——
落地与否一律以工作副本事实判定。

维护回合输出的是工具参数 JSON（逐字中文锚点 + 多条 edits），沿用正文的输出上限
容易被截断；补救手段是**要求模型拆短调用 + 提示用户调高设置**
（思考强度不由程序代改——主模型沿用户设置，子模型沿其模型默认配置），
而不是在程序里改写用户设定的 `max_output_tokens` / `reasoning_effort`。

### Lv.1 的两步流程（调研+正文 → 维护）

Lv.1 的世界状态 / 角色状态随**正文文本**携带（复用 Chat 的区块契约），只有
**历史（记忆总结）**走工具。记忆总结不再在正文前写入，而是在正文完成后由
**第二步单独的新请求**维护：

1. **第一步·调研**（`stage=prepare`，**文本零输出**）：先调
   `narrchat_readHistory` **一次**（历史的**唯一来源**；此前的 assistant 消息
   不含记忆区块）；需要现实资料时联网搜索（`narrchat_webSearch` →
   `narrchat_webFetchPage`，可多步）。**本步不写记忆、不写正文**：
   它只负责把事实依据（历史锚点 + 现实资料）备齐，模型写什么都一律丢弃
   （因此也不需要在文本通道写进度汇报）。回合上限 `kAgentMaxPrepFrames` = 6
   （联网一次典型 3 回合）。**退出条件**：本回合不再调用工具；或本回合工具
   **只有读取器**（读完历史且没有联网意图 → 立刻进入正文）。
2. **第一步·正文**（`stage=story`，**唯一正文上屏步**）：**调研结束后立刻**
   在思考通道定大纲并输出 5 个二级标题区块：`## 剧情演绎` → `## 推荐行动` →
   `## 当前时间` → `## 世界状态` → `## 角色状态`；**禁止**输出 `## 记忆总结`
   （它只以工具结果形式出现；应用侧采纳时仍会剥离），也不允许调用历史编辑器
   （状态编辑在第一步一律被拒绝）。回合上限 `kAgentMaxStoryFrames` = 8。
3. **第二步·状态维护**（`stage=state`，**单独新请求**）：正文完成后**无条件**
   发起。只维护记忆总结：根据正文里的 `## 当前时间`，用
   `narrchat_editHistory`（`op=append`）追加**恰好一条**
   `- {轮次} | {时间} | {记忆内容}`（{轮次} = 本轮轮号（裸数字）；
   {时间} = 正文的 `## 当前时间`）。若与历史旧条目 / 既有文案的写法冲突，
   **以新格式为准**（旧条目本身原样继承、不改写）。**档位 > 0 且未合并条目
   达到 2×档位时**，该调用还要把最旧的若干条合并为区间条目（见「记忆总结轮次
   合并」小节：脚本由应用在生成前算定并写进维护回合指令，完成判定并入
   `_maintenanceSatisfied()`）。维护步拒绝联网、拒绝改正文 / 世界 / 角色 /
   当前时间。回合上限 `kAgentMaxStateFrames` = 4。
4. **所有步结束后统一入库**：第一步结束**不写库**，第二步结束也**不写库**；
   只有全部步结束（含维护失败 / 取消被视为结束）才写入一条 `Round`。
   token 按主 / 子模型分桶：第一步归主模型，第二步启用子模型时归子模型；
   统计卡里再按「主模型 / 子模型 / 总计」合并展示。维护失败 / 取消沿用已有
   正文，另挂黄框警告。

为什么记忆条目**后于正文**维护：

- **从正文派生**：条目时间直接取正文 `## 当前时间`，不需要模型凭大纲先猜一个
  时间、再让正文去对齐；
- **省一次长上下文回读**：维护请求本身已经带着刚写的正文，模型直接总结即可；
- **失败不丢正文**：维护是正文之后的独立步骤，维护失败只影响记忆总结，
  正文仍然完整落库；维护文本也只进流式维护框，不会变成第二份正文。

落库快照仍是**混合**的：世界 / 角色 / 当前时间取自正文解析（与 Chat 同源），
历史取工作副本（维护工具落地）。

### 非创作步使用子模型（可选）

设置 → 通用设置 → 会话工作模式（实验性）→「非创作步所使用的模型（子模型）」：

- 默认「与当前激活主模型一致」；也可选任意平台 / 模型。配置键
  `agentSubagentPlatformId` / `agentSubagentModelId` 成对保存，任一为空即
  跟随主模型。
- **只作用于第二步状态维护**（当前唯一非创作步）。第一步调研 + 正文仍用主
  模型——它们共用同一段上下文与请求前缀，拆模型会让正文请求失去主模型缓存。
- 子模型与主模型「平台 + 模型」完全相同时**折叠为未启用**：请求仍走主模型，
  `round_stack` 四个子模型字段全 NULL，统计卡只显示主模型。
- 跨模型无法命中主模型的上下文缓存，设置页灰字提示：请确保子模型成本足够低，
  否则选择「与当前激活主模型一致」。
- 子模型按**自己的**温度 / 思考 / 最大输出 / 流式能力 / 默认思考强度请求；
  系统提示词不变，工具 schema 按子平台协议（Responses / Chat）重新生成；
  跨平台时 `baseUrl` / API Key 也取子平台。进入维护步前会断开
  `previous_response_id`（主模型的响应 id 对子平台没有意义）。
- 子模型不支持思考 / 识图时，维护步请求会剔除 reasoning、把图片内容块压成
  纯文本；这只影响**回传请求**，UI 思考聚合与 RAW 原文不变。
- 维护失败 / 取消语义不变：正文照常保留，另挂黄框警告。子模型必须支持工具
  调用（维护步靠 `narrchat_editHistory` 落记忆）。

#### Token 统计（主模型 / 子模型 / 总计）

`round_stack` 用四个可空列记录子模型：`subagent_model_name` /
`subagent_tokens_in` / `subagent_tokens_out` / `subagent_cached_tokens_in`：

- 四列全 NULL → 未启用子模型，统计卡只显示主模型；
- 任一项有值 → 统计卡分别显示主模型、子模型、总计（输入 / 缓存命中输入 /
  输出 / 缓存命中率 / 总 token）；
- 单个字段 NULL 仍是「该字段无数据」，显示斜体「（无）」；`0` 是真实 0；
- 四个子模型列不参与 `BackupDigest`，不升摘要版本，避免升级后全量同步冲突；
  统计随书库快照照常上传。

### 截断（`response.incomplete`）怎么处理

输出触顶时服务商发的是 `response.incomplete`（**没有** `error` 字段，只有
`incomplete_details.reason`）。旧实现把它和 `response.failed` 合并抛异常，
文案恒为「**API 请求中断：null**」，还会连带赔掉本轮已生成的正文。现在：

- 底层（`AiService.responses`）：保留截断前的正文与工具参数，标记
  `AiCallResult.incomplete` + `incompleteReason`，**正常返回不抛异常**；
  `failed` 仍抛，但文案兜底为「服务端未给出原因」，绝不出现 `null`；
- 执行器：给下一回合补一条「减少并拆短工具调用（一个栏目一次调用、edits 尽量
  少、不要复制长段文本）」的指令；截断的响应**不作为续接基点**（下一回合全量重发）；
- **不改请求体的 `max_output_tokens`**：各步都按用户设置原样发送，
  触顶属于用户可自行调节的参数，程序只提示不擅改；
- 末回合仍被截断 → 常驻提示首行给出可操作提示（去设置里调高「最大 token」）；
  正文一个回合都没产出时，失败条目的红框（`error` 级提示）也会写明「被输出上限截断」，
  原黄框内容并入同一条提示。

### 一轮的完整流程（`AgentRoundRunner`）

1. **组装**：`instructions`（档位对应的 `PromptMode`）+ 历史消息（Lv.1 最新一轮
   5 区块 / 更早仅正文）+ 当前用户消息；**不预置任何
   状态**——状态由模型主动调用对应栏目读取器获取。工具集 = 历史一读一写
   （`narrchat_readHistory` / `narrchat_editHistory`），联网强制开启时叠加
   搜索 / 打开页工具。
2. **第一步·调研回合（`stage=prepare`）**：契约要求先调
   **一次** `narrchat_readHistory`（历史的唯一来源，本回合只读一次），需要现实
   资料时联网搜索（`narrchat_webSearch` → `narrchat_webFetchPage`，可多步）。
   **本步不产出记忆 / 正文**：文本零输出（写什么都一律丢弃），
   回合上限 `kAgentMaxPrepFrames` = 6。**退出条件**：本回合不再调工具；或本回合
   工具**只有读取器**（读完历史且无联网意图 → 立刻进入正文）。
3. **第一步·正文回合（`stage=story`，唯一正文上屏）**：调研结束后**立刻**
   在思考通道定大纲，按书籍设定 / 文笔参考产出正文，输出 5 个二级标题：
   `## 剧情演绎` → `## 推荐行动` → `## 当前时间` → `## 世界状态` → `## 角色状态`；
   只有 `## 记忆总结` 被禁止并剥离（它只以工具结果形式出现）。
   第一步的状态编辑一律被**拒绝执行**（历史编辑器也不允许调用），
   记忆维护留到第二步。
   退出条件：本回合无工具调用；或**已采纳标题正文且本回合工具全是编辑器**
   （编辑器被拒，记忆交给第二步）。含搜索 / 打开页 / 读取器等**喂正文**的工具时
   继续下一回合（结果必须回到上下文）。回合上限 `kAgentMaxStoryFrames` = 8。
4. **第二步·状态维护（`stage=state`，单独新请求）**：正文完成后**无条件**发起。
   读取器优先复用第一步的历史结果：第一步已提供过历史全文时，维护步重复读取
   被拒绝；第一步漏读时允许补读一次。指令（`[State-maintenance turn]`，中文、
   不加语言标记）要求**只维护记忆总结**：根据正文 `## 当前时间` 用 `op=append`
   追加恰好一条本轮条目，需要合并时补 `op=set`。维护步拒绝联网、拒绝改正文 /
   世界 / 角色 / 当前时间。
   维护回合「空手回合」（只回文本 / 只试探读取）**不会提前结束**：
   只要记忆仍不完整就继续修复，回合上限（1 主 + 3 修）兜底。
5. **所有步结束后统一入库**：工作副本快照合并进本轮 `Round`（Lv.1 的世界 /
   角色 / 时间另取正文解析结果；每轮仍存全量快照六字段，侧边栏可编辑、云同步与
   历史结构零改动）。**不按步入库**：第一步正文完成、第二步维护完成都不写库；
   只有全部步结束才写一次；token 按主 / 子模型分桶（第一步归主模型，
   第二步启用子模型时归子模型，统计卡再合并出总计）。
   **不再有「文本状态兜底」**——工具维护的栏目只能经工具落地，正文里违规出现的
   对应区块**剥离后**才写入正文（Lv.1 的 `## 世界状态` / `## 角色状态` 是合法
   正文段，直接落库）。
6. **提示（同一框体，按级别着色）**：
   - 生成期间：正文下方显示「状态维护」流式框，维护文本与工具过程只进这个框；
   - 维护成功：该轮气泡 footer 显示灰色临时提示「状态维护已完成」；提示只在
     内存里，**下一轮开始 / 关闭 APP 即消失**，不写库、不参与云同步；
   - 维护未完成 / 失败 / 取消：正文仍落库，另挂**黄框常驻警告**
     （`RoundProvider.roundWarningsFor`），内容 = 仍存在的缺口 + 维护失败原因；
     **没有关闭入口**，随代持久化 + 云同步，重生成 / 切换 / 删除该轮时随代变化；
   - 正文为空的 Agent 轮（模型只返回工具调用）：本轮**不写库**、用户输入走既有
     「失败条目」（可一键重试），提示并入该轮的**失败占位代**（`error` 级）
     说明「状态改动已作废」。
7. **取消 / 失败**：
   - 第一步取消 / 失败：本轮不入库，落失败条目（与 Chat 一致）；
   - 第二步维护取消 / 失败：**正文仍按“所有步结束”统一入库**，并挂黄框
     「状态维护未完成 / 已中断」；不新增错误代、不丢正文。

### 「读完再写 → 直接改」：为什么维护步不再重复读取

模型的默认习惯是「写完再查一遍再改」（读到一次状态 → 写正文 → 维护再读一次
→ 才动手编辑）。这一次重复读取要额外花掉一个回合，且会把此前那份读取结果从
上下文中**顶替**掉（同栏只保留最新一份）。而状态在写正文时**不会变化**——只有
编辑会改变它——所以维护步的锚点就是此前那一份。Lv.1 同理：**调研步读取一次，
维护步直接复用**。为此：

- **提示词**：`prompt_v2_sections.dart` 的模式契约与维护回合指令都明确
  「重复读取会被拒绝 / 锚点从对话中已有的结果逐字复制」，
  并要求**第一个维护回合就完成**（经 `promptInterface.stageState` 取用）；
- **执行器护栏**（`_refusedRepeatRead`）：**维护步**对
  **本轮已提供过全文的栏目**的读取调用**不执行**，回传一行说明（工具框显示 ✕，
  不计入缺项清单）并提示直接调用对应编辑器；被拒绝的读取**不会剔除**此前那一份
  结果（它仍是唯一锚点来源）。已提供过 = 该栏目读取器成功返回过 / 该栏目编辑器
  回传过全文（成功与失败都回传）。调研回合正在读取的调用不受影响；调研回合已提供
  过历史全文时，维护回合再调 `narrchat_readHistory` 会被拒绝。
- **非合规流程不失明**：漏读的栏目、参数被截断的读取，护栏一律放行
  （照常执行）——模型仍能自我修复。

在合规流程下，维护步因此只需**一个回合**（直接编辑），而不是「一回合读取 +
一回合编辑」。

### 缺口判定

| 缺口 | 触发条件 | 维护回合指令 |
|---|---|---|
| `sectionUntouched` | 栏目既没被编辑、也没 `op=noChange` 声明 | 调用一次**该栏目的编辑器** |
| `sectionUnchanged` | 做过编辑但整栏与上一轮逐字节相同（历史栏除外） | 按最新读取结果做实际编辑 |

当前只判定**历史**一栏。框架里还留着世界 / 角色的多栏目判定与
`lazyCharacters` 懒修改检查（角色块逐字节比对），当前不触发（见「已移除：Agent Lv.2」）。

当前时间**不参与**缺口判定：它属于正文（`## 当前时间` 小节），
缺失时工作副本沿用上一轮时间（正文质量问题，不作状态缺口）。

## 上下文构成（前缀缓存友好）

各步的 `instructions` 与 `tools` **逐字节相同**（后续步不裁剪规则、
不换工具集），历史前缀也相同，只有尾部不同 —— 服务商的 prompt cache 在
调研 / 正文 / 维护回合与下一轮都能命中。

**例外**：启用非创作步子模型（且与主模型不同）时，维护步是另一个模型 /
平台，**跨模型不共享缓存**；这正是设置页灰字提示「确保子模型成本足够低」的
原因。主模型第一步内部（调研 → 正文）的前缀仍完全一致、缓存照常命中。

- **历史里的 assistant 消息形态随档位**（`AssistantHistoryShape`）：
  Lv.1 最新一轮带 5 区块、更早仅正文；Chat 维持原样。
  这是稳定性的关键：历史中一旦出现 `## 记忆总结`（Lv.1），模型就会照抄它。
- **状态**由模型**主动调用**对应栏目读取器获取（**真实注册**的只读工具，
  不预置、app 不伪造条目）：返回值永远是**工作副本当前渲染**
  （Lv.1 调研回合读取 = 上一轮库内状态；维护回合的重复读取在合规流程下
  被护栏拒绝），
  应用侧无需从调用序列区分步骤。结果以 `function_call_output` 形态进入
  上下文——**工具结果，不是输出格式**，不会诱发模型模仿 md 格式把状态
  写进正文；
- **每栏只保留最新一份**读取结果（按工具名剔除旧份，且只有**真正执行成功**的
  读取才剔除旧份——被拒绝的重复读取不得顶掉模型唯一可用的锚点来源），
  输入不随修复回合膨胀；
- **思考块**（`reasoning` 条目）不参与上述剔除：它是服务商「带工具请求必须逐块
  回传」的硬要求（见上文「思考块回传」），每回合按**工具调用数**各发一块、
  按响应顺序累积（剔除过期读取调用时，其紧邻的那一块随笔随删）；
- 读取结果只含**被请求的那一栏**块（`<worldState>` / `<characterState>` /
  `<memorySummary>`，空栏目标 `empty="true"`），与 `Round` 字段一一对应；
  时间不在其中（属于正文 `## 当前时间`）。
- **不约束思考链**：提示词不限定思考的语言与写法（不要求「思考用英文」一类），
  思考链不是输出内容；功能性步骤照旧（调研回合读史、正文**立刻**写、
  维护回合只在第二步做）。
  思考块本身会随回合回传（服务商要求，见「思考块回传」），因此它同样计入输入
  token 与缓存前缀。
- **修改轮（Chat 页 AI 气泡的「按意见修改」）**：历史 = 被重写轮**生成时收到的
  n 轮 + 该轮自身**（n+1，`RoundProvider.modifyRoundByOpinion`），工作副本的
  `roundIndex` = 被重写轮、基座 = 该轮的**上一轮**——因此读取器读到的历史停在
  上一轮，本轮记忆条目仍按被重写轮的轮号落地（`op=append` 校验的轮号即被重写
  轮号）。落库 = 该轮同分组**新增一代**（旧代留在版本树可切回）。

## 协议兼容降级（就地重发同一回合，不烧回合预算）

`_callFrame` 捕获 `AiExceptionKind.api` 的 4xx 类错误，就地降级后重发**同一回合**
（`_frames` 不计数，工具不重复执行；同一回合至多连降 3 项）：

| 症状 | 降级动作 |
|---|---|
| 报错含 `previous_response_id` | 本回合改为全量重发 input |

**思考强度不参与降级**：执行器不为任何主模型回合覆盖 `reasoning_effort` /
思考开关（历史上的「记忆 / 维护回合降为 `low`」已取消——用户设置是唯一真源）；
启用子模型时，维护帧用子模型自己的默认思考强度与能力。任何一侧被服务商拒绝，
都是普通 API 失败（不重发、不回落）。

只有**内容校验失败**（锚点未命中、记忆缺本轮条目等）才消耗修复回合。

### 思考块回传（带工具的请求必须**逐块**回传 reasoning）

服务商对**携带 `tools` 的请求**有硬性要求，且校验粒度是**逐个工具调用**的
（下表为针对 DeepSeek 官方 `/responses` 线路的**实测**结论）：

| 请求形态 | 结果 |
|---|---|
| 每个 `function_call` 前各一块非空 `reasoning` | **200** |
| 一回合调 N 个工具，只回传 1 块思考 | **400** |
| 某块 `reasoning_text` 为空 | **400** |
| 只回传 assistant 正文、没有 reasoning | **400** |
| 完全不回传 reasoning | **400** |
| 块 id 形态（同 id / 异 id / 无 id） | 均 200（**不校验 id**） |

报错文案：`The reasoning_text in the thinking mode must be passed back to the
API`（Chat 通道为 `content[].thinking`）。这也解释了历史现象：记忆 / 维护回合
一回合通常只调一个工具，一块思考恰好够用；**调研轮 / 正文回合一回合并发调两个工具**
（如 `narrchat_readHistory` + `narrchat_webSearch`）时只发一块 → 必 400。

因此 `AiService` 除聚合文本（`reasoningContent`，界面用）外，还**按条目**捕获
思考块（`reasoningItems`：id / 文本 / 文本形态）；执行器把它挂在 `_frameReasoning`
上，**追加每个 `function_call` 时各发一块**（`_appendCallItems` 按 `callIndex`
取块），无工具调用的回合则在正文前发一块。剔除过期读取结果
（`_pruneStaleReadState`）时**连同紧邻其前的思考块一起剔除**，避免思考掉到会话
开头变成「没有归属的孤儿块」。

两种线路由 `wire_adapters` 还原成各自的回传形态：

| 线路 | 回传形态 |
|---|---|
| Responses | `{type: 'reasoning', id?, content/summary parts}` input item（顺序：每块 reasoning → 其所属的 function_call → function_call_output） |
| Chat | assistant 消息上的 `reasoning_content` 字段（纯工具回合会补一条 `content: null` 的 assistant 承载它与 `tool_calls`） |

联网搜索的工具循环（Agent 关档位）走同一份机制：`AgentRunner` 同样按调用数各发
一块（Responses 线路在展开时还原成 reasoning item；Chat 线路忽略这些条目、改用
同条消息上的 `reasoning_content`）。

两条实现约定：
- **文本形态随响应**：`content` 形态与 `summary` 形态各自按其原形态还原
  （OpenAI 侧 reasoning 的 `content` 是加密形态，纯文本只允许放 `summary`）；
- **不伪造内容**：模型未产出思考时（未开思考 / 服务端没给）不回传凭空编造的
  思考；但**工具调用回合的缺块仍按回落链补齐**（该回合正文 → 占位文本）——服务端
  对缺块是硬 400，宁可回传一段不完美的文本，也不能让整轮生成失败。

#### 思考链压缩（按「步」而不是「回合」）

思考块随每回合全量重发而累积进输入。实测（`deepseek-v4-flash`，约 800 字思考，
同一请求只换块内容）：

| 会话回合数 | 回传真实思考 | 回传最小块 |
|---|---|---|
| 1 | 797 | 641 |
| 2 | 1070 | 758 |
| 3 | 1343 | 875 |
| 4 | 1616 | 992 |

即输入按 **+273 token/回合**（真实思考）vs **+117 token/回合**（最小块）增长。
`ExperimentalSettingsProvider`（设置 → 通用设置 → 会话工作模式（实验性））提供两级开关：

- **主开关「压缩非正文步模型所获取到的思考链」**（默认**开**）：
  Agent Lv.1 的**第一步 = 正文步**（包含调研 + 正文两个回合），第一步收到的
  思考链保持完整；只有**第二步维护步**（非正文步）收到的前面思考链被压缩。
  维护步自己的后续修复回合也压缩。
- **子开关「压缩所有回合的思考链」**（默认**关**，**仅主开关开启时显示**）：
  开启后第一步的调研 / 正文回合也压缩，即所有回传思考都压缩。
- 主开关关闭：所有步完整回传；子开关隐藏并复位为关。

压缩规则：按**段落**切分、丢弃纯空白行；**单段原样返回**；**多段取首段 + 末段**。
只改**回传给模型**的内容，UI 思考框、RAW 返回区和 `reasoningContent` 聚合仍是
完整原文。完全不发 / 只发最后一个调用的块 / 空文本 / 用正文顶替实测均为 400，
可调的只有体积。

配置键：主键 `agentCompressNonBodyReasoning`（缺失默认 `true`）、子键
`agentCompressAllReasoning`（缺失默认 `false`）；旧键
`agentReasoningReplayReduced` 只读迁移（新键缺失时沿用旧值，尊重老用户手动关闭）。

有状态续接（`previous_response_id`）与压缩冲突时的处理：

- 主开关开、子开关关：第一步仍可续接；进入第二步前断开续接、全量发送
  压缩后的会话，确保维护模型真正收到压缩版；
- 子开关开：整轮不使用续接，所有请求都发送压缩后的 reasoning；
- 主开关关闭：续接行为完全不变。

### 降级重发的成本（不计回合 / 不计失败轮 / 不计 token）

降级只针对**协议能力探测**（当前唯一一项：服务商是否接受 `previous_response_id`
有状态续接）：结论只在**本轮**内生效（本回合改为全量重发），**跨轮不记忆**——
下一轮会重新按平台能力设置试一次。这是刻意的：探测失败的成本极低，而记忆会引入
「服务商补齐支持后仍长期不发」的过期状态。

被拒绝的那次探测回合**不是一次失败**，具体地：

- **不计回合**：`_frames` 只在调用真正返回后自增 → 降级重发不算回合数（`AgentRoundResult.frames` 不含它）；
- **不计失败轮**：异常在 `_callFrame` 内被吞掉后就地重发 → 不产生失败条目（`FailedAttempt`）、
  不触发「错误重连……（x/3）」（那是网络类整轮重试的提示）、不产生常驻提示，本轮照常落库；
- **不计 token**：参数校验类 4xx 在服务端推理前即被拒绝，不返回 `usage`；应用侧本轮用量
  只累加**成功回合**，所以 `tokensIn` / `tokensOut` / `cachedTokensIn` 都不含它；
- **不重跑整轮**：4xx 属 `AiExceptionKind.api`，`_callWithRetry` 只对网络类失败整轮重试
  → 已产出的正文（已花的 token）不会被作废重发。

唯一的成本是**一次额外的 HTTP 往返**（通常几百毫秒），加上 RAW 里多一条记录。

### RAW 里的失败信息

失败的那次交换会记录原因（`RawExchange.error`），RAW 显示
**`请求失败：API 请求失败（HTTP 400）：<服务商报错原文>`**（含 HTTP 状态码）；
既无错误也无返回内容时才显示「（无 AI 返回内容）」。整轮失败时（例如 4xx 无法降级、
网络重试耗尽）该次交换同样带着这条说明出现在「失败轮」的 RAW 里。

## 单轮链式续接（previous_response_id）

默认**关闭**：`previous_response_id` 仅用于“单轮内多次调用”的续接回合，
**永不跨轮**（历史轮次与记忆结构不变，请求体形态跨预算一致）。

- 平台设置 →「允许链式续接（previous_response_id，需服务商支持）」默认关；
- DeepSeek 官方为**无状态 API**（`previous_response_id` / `conversation` /
  `store` 均不支持且静默忽略），关闭时每回合全量重发输入；
- OpenAI 官方等有状态实现可开启：续接回合只发新增输入项（`tools` /
  `instructions` 一并省略）；
- **启用子模型时**：主模型第一步内部仍可按平台能力续接；进入第二步维护前
  无条件断开（主模型的响应 id 对子模型 / 子平台没有意义），维护步全量发送。

## 锚定式编辑（状态栏目）

参考 DeepSeek Harness / Claude 系工具的行级定位机制——**不用行号**（LLM 数行号
不可靠，是「改错行 / 记忆替换第一行」的根源），改为**原文锚点 + 唯一匹配**：

- 六个工具**按栏目成对拆分**（世界 / 角色 / 历史各一读一写），编辑器只改
  自己那一栏：`edits` 只携带**变更的行**；`before` 必须从**本栏目读取器**的
  结果中**逐字复制**（可含 `\n` 连接连续多行）。当前只注册历史这一对
  （`narrchat_readHistory` / `narrchat_editHistory`），世界 / 角色两对是保留
  框架（见「已移除：Agent Lv.2」）。匹配三级递进：逐字行 →
  归一化行（折叠空白与全/半角标点）→ 归一化行内子串；
  - 未命中 → 报错（提示逐字复制 + 当前行数 + **该栏目当前全文**供重锚，至多 400 行）；
  - 不唯一 → 报错（列出命中行号，引导补充唯一上下文）；
  - 命中 → 只替换该段行，未触及的行字节级保留；
- `op=append` 追加到栏目末尾（历史条目固定用它）；`set` / `insertAfter` /
  `delete` 均以 `before` 锚定；`op=reset` 仅限空栏目 / 首次填入 / 明确重排；
- `op=noChange` **必须携带非空 `reason`**（省略栏目 ≠ 声明无变化），登记进
  `declaredUnchanged` 供缺口判定放行；历史栏**不接受** `noChange`；
  noChange 是**最后手段**：正文里角色/局势只要有新动向（一句反应、一段心理、
  一次移动本就是「变化」），就应写一条 `op=set`；一次调用可带**多条** `edits`
  （每条对应一行改动），提示词与工具描述明确点名「无需大改」这类空泛理由会被
  视为懒修改；
- 同一调用内按顺序应用（锚点在应用时刻解析），**事务化**：任一编辑失败整体不提交；
- 结构性校验：历史（记忆总结）变更后必须恰含一条本轮（轮次 = N）条目
  （解析与计数见 `lib/utils/memory_entry_format.dart`，新格式
  `- {轮次} | {时间} | {记忆内容}` 与旧格式 `- 第N轮｜日期：…｜…` 一并兼容）；
  **合并区间写法**（`- 11~15 | …` / `- 11 - 15 | …`，半角 `-`/`~` 与全角
  `－`/`～` 均可，两端升序归一并保留原分隔符）视为**区间内各轮均已存在**：
  `memoryEntryCount(text, 13)` 对 `11~15` 计 1。档位 > 0 时该校验还要求
  **本轮应做的合并已落地**（见下节）；
- **当前时间不设工具**：属于正文 `## 当前时间` 小节，正文采纳时由应用解析
  写入工作副本（缺失则沿用上一轮时间）；
- 工具结果分两面：`summary`（UI 一行）与 `modelOutput`（回传模型全文，含栏目
  当前全文）；参数被截断（`argumentsUnparsable`）时不执行，回传「一栏目一次
  调用」的重试指引。

### 记忆总结轮次合并（档位驱动，Chat / Agent 一致）

每本书的「记忆总结轮次合并」档位（`books.memory_summary_rounds`：0 = 关闭、
5 / 10 = 每个合并项包含的轮次数）决定记忆栏是否把散条目压成区间条目。规则与
落地口径的**单一真源**是 `lib/services/memory_merge_planner.dart`：

- **标准形态**（`kMemoryMergedEntryFormat`）：
  `- 15 - 20 | 仙历十四年五月二十日 ~ 仙历十四年七月八日 | 这期间的事。`
  （轮次区间用 ` - `、时间区间用 ` ~ `）。模型按全局 Markdown 规则把 `~` 转义成
  `\~` 时，解析层用 `unescapeMemoryEntryText` 还原，展示 / 判定都不带反斜杠
  （区间分隔符前置的 `\` 同样容忍）。
- **触发规则**：档位 T > 0 时，**未合并条目**（未被任何区间条目覆盖的单轮条目）
  达到 `2T` 即把**最旧的 T 条**合并为一条区间条目，并重复到剩余未合并条目
  `< 2T`（积压可在同一轮内补齐）。例（T=5，已有区间条目 1-7，散条目 8/9/10）：
  第 11~16 轮都不动作，第 17 轮（未合并 = 10 条）合并 `8-12`。
- **不变量**：已合并条目冻结（不改写 / 不拆分 / 不重排）；本轮新增的那一条永不
  落入区间（区间个数 k 恒满足 `k*T <= count - T`）；尾部未合并片段末条不是上一轮
  （历史缺口 / 乱序）时本轮不动作；档位 0 只注入「不主动合并、已有区间条目原样
  保留」。
- **用户要求优先**：策略文案与 Chat 的本轮指令都写明「若本轮用户输入明确要求
  别的合并方式（或要求不要合并），以用户要求为准」，应用**不做**关键词检测。
- **下发与判定**：计划在**生成之前**一次算定（输入 = 上一轮落库的记忆总结 +
  档位 + 本轮轮号）。Chat 走用户消息（后置词之后，模型改写 `## 记忆总结` 区块）；
  Agent 走维护回合指令（一个 `op=set` + 多行 `before` 完成一个区间的
  合并，随后照常 `op=append`）；生成后用
  `isMemoryMergeApplied` 判定（每个区间存在**恰好覆盖它**的合并条目）。
- **未落地的处置**：Agent 的维护步把「合并已落地」并入 `_maintenanceSatisfied()`
  继续重试；重试回合用尽、或 Chat 模式（无回炉
  机会）→ 轮次卡片一条常驻警告（`MemoryMergePlan.uiText`），**不阻断正文**。

## 其它交互

- **正文采纳制（最后一个标题回合胜出）**：本轮正文 = 正文步 **最后一个**含
  `## 剧情演绎` / `## 正文` 标题的回合的原始内容；无标题 + 带工具的回合是**开场白**
  （「我先搜索一下…」），不上屏、不采纳、不阻塞真正正文；无标题 + 无工具的回合
  按未按格式输出的正文兜底。门控 `_FrameGate` 在每个回合正文首次出现前发
  `AiStreamChunk(narrativeReset)`，界面表现为正文块重置重流（不是拼接）；
- **块顺序**：思考 / 搜索 / 打开页 / 状态工具按 **AI 返回顺序**流式展示；
  正文是「块外」特殊块，插入在其返回位置；
- **统一工具块**：联网搜索 / 打开页面 / 状态工具共用同一形态，标题统一为
  `Tool · 工具名`（Chat 模式保留语义化标题；状态工具当前只注册历史一读一写）；
  **一次工具调用只产生一个框**
  （流式预览 / 开始 / 完成共享同一事件，按 callId 匹配）；执行中自动展开明细，
  成功自动收起为一行，失败保持展开完整原因（黄 = 页面拒绝访问，红 = 校验失败）；
- **提示词**：规则一律**简明中文**（v2 口径；英文只保留工具名、状态块标签与
  `[State-maintenance turn]` 回合标记），字面量与标题名永不翻译；
  **工具 `description`** 同样中文，不加`【中】`一类语言标记；
- **联网搜索**：Agent 期间强制开启，与状态工具同批注入
  （`narrchat_webSearch` → `narrchat_webFetchPage` → 正文 + 状态工具）；
  **system 不追加任何联网指令**——何时调用、搜索后必须打开页面等要求全部写在
  两个工具的 `description` 里（见 `docs/agent_tools.md`）；
- **视觉**：Agent 模式支持图片输入（responses `input_image` 内容块，仅视觉模型）；
- **非流式**：Agent 期间流式强制开启；模型能力关闭流式时整轮（含维护回合）全非流，
  由 `NonStreamReplayer` 回放，同样经过回合门控；
- **RAW**：RAW 对话框 AI 返回区为「思考块 / 工具调用块 / 正文块」，
  每回合一条交换记录（含维护回合）；Agent 交换按**轮 → 步 → 回合**插入分组头
  （第 N 轮 / 第一步·调研与正文 / 第二步·状态维护 / 第 N 回合；回合序号在每一步内
  连续编号，不再重复写「调研回合 / 正文回合」），Chat 交换保持原平铺时间线；
  **预览请求体 = 实发首回合**（Lv.1 = 调研回合），
  并在对话框里列出后续**可能**发出的回合（正文 / 维护，
  仅展示相对上一回合的增量字段）——是否发出取决于模型响应。

## 设置页（通用设置 → 会话工作模式 → Agent 模式）

- 分区标题是**「会话工作模式（实验性）」**：分区标题与卡片内四行选项标题
  （「Agent 模式」「非创作步所使用的模型（子模型）」
  「压缩非正文步模型所获取到的思考链」「压缩所有回合的思考链」）
  都带**黄色「（实验性）」**标注——颜色取主题警告色（`NarrChatColors.warning`，
  与对话页「搜索(BETA)」同款黄色），统一由设置套件的 `SettingsTitleText` 渲染；
- **整张卡片任意位置可点**即可展开档位菜单（不必对准右侧箭头）；
  实现用 `MenuAnchor`（与对话页模型选择器同款交互）而非 `DropdownButton`
  ——后者的展开热区只覆盖按钮本身；
- 卡片内只有**简要**介绍：调用自定义工具（`narrchat_*`）走两步生成、
  由 Agent 托管记忆总结、⚠ 档位开启期间模型已支持的功能（思考 / 流式 / 搜索）
  无法通过对话页指示器关闭、**未来更新可能对本功能做出破坏性变更**、正确性不保证；
- **各档位差异写在下拉选项内**（标题 + 一行说明）：

  | 选项 | 说明 |
  |---|---|
  | 无 | 使用传统 Chat 方式 |
  | Agent Lv.1 | 记忆总结部分将由 Agent 托管 |

- 档位保存到本地配置 `agentModeLevel`（0 = 关 / 1 = Lv.1）：非 int、未知值
  （包括已移除的旧值 `2`）一律按「关」处理；更早的布尔键 `agentModeEnabled`
  已废弃，不再读取（配置里残留 `true` 也当没有）。读取过程**不写盘**，
  只有用户切换档位时才写入新键；
- **「非创作步所使用的模型（子模型）」**：行内展示灰字提示与当前选择，
  点击打开「与当前激活主模型一致」+ 按平台分组的模型选择器。保存到
  `agentSubagentPlatformId` / `agentSubagentModelId`（两项成对，空 = 跟随
  主模型）；Agent 轮只在第二步状态维护生效，详见上文「非创作步使用子模型」；
- **主开关「压缩非正文步模型所获取到的思考链」**（Agent 模式专用，**默认开**）：
  第一步（调研 + 正文）视为正文步，思考链完整；只压缩第二步维护收到的前面
  思考链。保存到 `agentCompressNonBodyReasoning`；
- **子开关「压缩所有回合的思考链」**（**默认关**，**仅主开关开启时显示**）：
  开启后第一步的调研 / 正文回合也压缩。保存到 `agentCompressAllReasoning`；
  主开关关闭时子开关隐藏并复位为关；
- 旧键 `agentReasoningReplayReduced` 只读迁移（新主键缺失时沿用旧值，尊重
  老用户手动关闭）；规则与实测数据见上文「思考链压缩」。

## 已知限制

- 常驻提示挂在**「代」**上（`round_stack.message`，v21 起随代入库并随轮次部件云同步）：
  跨设备可见，但**双端各改不同代的提示不做逐代合并**（冲突时整部件取舍，最后写入者胜）；
  旧版本（≤v20，不认识该列）读库时会忽略这两列，也不会清掉它们；
  旧快照整体替换版本树时提示会随之被覆盖（与轮次部件同粒度）；
- Lv.1 的历史（记忆总结）无法再依赖「上一轮 assistant 消息」传递，模型必须在
  **调研回合**主动调用 `narrchat_readHistory`（**只读一次**）；漏读时正文可能
  缺少历史依据（应用侧不兜底，维护回合才允许补读一次）；
- 记忆条目由**正文之后的维护步**总结：维护失败 / 取消时正文照常入库，但本轮
  记忆条目可能缺失；应用侧**不会自动回补**，黄框会一直提示到该轮被重生成 / 删除；
- 所有步结束才统一入库：生成中途关闭 APP，本轮不会保存（包括已生成的正文）；
- 记忆条目的时间取**正文 `## 当前时间`**；维护步据此写条目。时间不参与缺口
  判定，两者不一致属正文质量问题；
- 云同步 / 书籍迁移不感知 Agent 档位（数据形态与 Chat 完全一致，无迁移要求）；
- **子模型（非创作步）**：必须支持工具调用，否则维护步无法落记忆（正文仍保留，
  黄框提示维护失败）；子模型不支持流式时，维护过程没有流式文本，结果在请求
  结束时一次落地；跨模型无法命中主模型的缓存，成本提示见设置页；子模型统计
  （`round_stack.subagent_*`）不参与内容摘要，随快照上传但不单独触发同步；
- 子模型配置的平台 / 模型被删除或改名时，生成侧自动回退「与当前激活主模型一致」，
  不会拿一个不存在的模型发请求；配置键本身可能残留，改回设置页重新选择即可；
- 维护步的重复读取护栏按「本轮是否已把该栏目全文交给模型」判断：模型
  完全没读且编辑器从未回传过该栏目的极端情形下，重复读取照常执行（宁可多花一回合，
  也不让模型失去锚点来源）。
