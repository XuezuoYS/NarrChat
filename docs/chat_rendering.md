# 对话页怎么渲染和滚动

> 这一页是应用里最复杂的界面：几百轮对话、流式生成、图片、可切换版本、分支。
> 本文说明**为什么这么设计**，以及改动时要小心什么。

## 一句话

列表只渲染"窗口"里的轮次；**第 N 轮在哪**由一个覆盖全书的几何模型算，不靠问滚动容器；
右侧那条轨道读同一个模型，所以拇指、进度、跳转三者永远说的是同一个数。

## 分层

```
数据    RoundProvider.rounds（活动链 + 分组）
  ↓
条目      ChatItem / ChatItemKey        一个气泡 = 一个条目（轮 uuid + 类型）
  ↓
几何      ChatGeometry                   全书条目高度前缀和（Fenwick）
  ↓
窗口      ChatWindowController           只决定"哪些轮参与渲染"
  ↓
定位      ChatViewportController         滚动 / 跟随 / 跳转 / 当前轮 / 进度 / 速度
  ↓
组件      ChatRail                       右侧轨道 + 面板
  ↓
页面      chat_screen                    把窗口切成行、回报实测高度、摆布局
```

对应文件：`lib/chat/chat_item.dart`、`chat_geometry.dart`、`chat_window.dart`、
`chat_viewport.dart`、`chat_locator.dart`、`chat_rail.dart`、`chat_rail_handle.dart`、
`chat_rail_motion.dart`、`chat_row.dart`、`chat_height_bucket.dart`。

## 为什么不用 `ScrollController.maxScrollExtent`

窗口化之后滚动容器里只有**一窗**内容，它的 extent 只反映这一窗，不是全书。
旧实现（真正的"滚动条跳舞"）就是因为拇指读这个值，每次窗口变化拇指都跳。
现在：拇指读几何模型，进度 = `(窗口基准 + pixels) / (全书总高 − 视口高)`。

同理，**不要拿 `maxScrollExtent` 的增量当"内容长了多少"**：它是懒加载估算值，
实测有一次增量为正、真实内容却在缩短（方向都是反的）。

## 坐标口径（改动时先看这一段）

消息列是 `reverse: true`：`pixels = 0` 是**列表最新一端**。设窗口对应几何下标 `[a..b]`：

```
base      = geometry.offsetOf(b)                        // 默认：窗口最新端距书底
bookOff   = base - leadingInset + pixels                // 视口底边在全书里的位置
progress  = bookOff / max(1, total - viewport)          // 0=贴底 1=顶部
currentRound = 视口顶部命中的**真实渲染行**（找不到时才用
               geometry.roundIndexAtOffset(bookOff + viewport) 兜底）
跳转落点   = geometry.topEdgeOf(index) - base + leadingInset - viewport
```

`leadingInset` 是"贴在最后一行底部的那段避让留白"（下面会讲为什么在那儿）。

**页码为什么不读几何**：几何里没构建的行只有估算高度，`maxScrollExtent` 也会随
懒加载构建进度变化；拿它们反推“视口顶是哪一轮”，长轮次滚动时数字就会随机跳，
甚至出现不存在的轮号。现在每个 `ChatRowMeasure` 挂载时登记真实渲染对象，帧末读
它们的全局矩形：视口顶部压着哪一行，页码就是哪一轮。坐标变换只在帧末做，长度
变化时再通知轨道刷新——不在布局阶段读坐标，也不会整页重建。

**显式轮次跳转用另一套 base**：页面把目标轮变成窗口第一行 `a`，再用当前列表的
**真实本地边界**反推：

```
base = geometry.topEdgeOf(a) + leadingInset - maxScrollExtent - viewport
```

这里的 `maxScrollExtent` **只表示当前窗口列表的边界**，不代表全书，也不拿它的增量
当内容增长。目标就是首行时，跳转落点化简为 `maxScrollExtent`（链首还要扣掉顶部
留白 / 分支头的高度）。这样落点不再包含目标之后几十个**还没构建、只有估算值**的
行；旧写法假设"窗口内行都会被实测"，在懒加载长书里不成立，越早的轮次累计误差越大，
正是"差出好多轮"的根因。

## 右侧定位器：一颗小滑块 + 五个独立部件

**不是滚动条**。滚动条的拇指要"长度表示视口占比、位置表示进度"，在窗口化列表里这两个数
只能来自几何模型，稍一变窗就跳；而且用户要的是"上下拖一下就能翻页"。所以：

| 部分 | 形态 | 行为 |
| --- | --- | --- |
| 滑块 | 10dp 宽的蓝色细手柄（44dp 高，拖动时 12dp），在**可读区**（输入面板以上）垂直居中 | 拖动时**跟着手指走**，松手 900ms **过阻尼**回中 |
| 行程 | 按轨道高度自适应：`(轨道高 − 滑块高)/2 − 12`，夹在 [120, 420] | 大屏能拖得更远；越往外每像素换来的速度越高 |
| 拖动语义 | —— | 速度只跟"离中央多远"有关（`ChatRailMotion`，满量程 = 整段行程，死区 6dp，满速 6.5 视口/秒），**不是位置映射** |
| 展开面板 | 4 个 40dp 圆形按钮 + 1 个 120×44 胶囊，**各自独立的 Material（底色 + 圆角 + 细边 + 轻阴影）** | 不是一个大面板包住五个部件 |
| 胶囊 | 左半 `当前轮 / 最大轮号`（当前轮加粗），右半跳转 | 点数字就地输入；放不下时整体缩放，不裁字 |
| 收起态拖动 | 页码胶囊淡入（140ms）+ 从滑块侧滑出，跟随滑块纵向 | 松手停留 1.2s 后淡出（220ms） |
| 显隐 | 内容不足一屏 / 只有一轮时不渲染；触控静置淡到 55% | 桌面常显（94%），拖动/悬停不透明 |

**回中为什么用指数衰减**：`offset(t) = from × (e^{-k·t} − e^{-k}) / (1 − e^{-k})`。
t=0 正好等于松手时的位移（不会瞬间跳到相反一侧），全程不越过中央（不振荡），末尾很长一段
都在慢慢贴合中央 —— 这就是"阻尼大"的观感。别换成 `Curves.easeOut` 之类再做符号运算：
`(value − 1) × from` 这种写法会在第一帧把滑块翻到**反方向**（真实踩过的 bug，测试里逐帧守着）。

为什么滑块不做进度：进度由胶囊里的页码直接读，比"拇指长短"更准也更好看；不做位置映射
就不会出现"手指到了、内容还没到"的撒谎观感。

配色：滑块用品牌蓝（`primary`，拖动/悬停更实并带柔光）；部件底色跟随亮暗主题
（浅色 = 白，深色 = `surfaceContainerHighest`，否则和背景几乎同色看不出是独立部件）。

**轨道只占输入面板以上那段右缘**：命中带不会盖住输入面板右上那排方形按钮，所以那排按钮
照常右对齐（不需要留空让位）；面板与滑块也以这段可读区的中心为准，视觉上更居中。

## 几何覆盖全书，窗口只管渲染

- 几何按**整条活动链**重建（2000 轮 ≈ 4000 条目，Fenwick O(n) 建树、O(log n) 更新）；
- 窗口变化**不重建几何**，只换渲染行（`_computeWindowItems`）；
- 待定气泡（生成中的用户消息 / 流式插槽）也进几何：它们的高度不记账的话，
  生成期间列表本地坐标和全书坐标会多出一段未知量，跳转落点跟着偏。
- 待定气泡**落在哪一轮**由 `RoundProvider.pendingRoundIndex` 决定：普通发送 = 链尾 +1，
  重新生成 / 修改并重新提问 / 按意见修改 = **被重写的那一轮**。生成期间页面只让
  「目标轮之前」的轮次进几何（目标轮的旧代与后续轮本来就将在完成后被取代），待定气泡
  因此画在目标轮原本的位置；滚动条 / 当前轮 / 最大轮号读的是同一份几何，不会谎报下一轮。

## 高度从哪来

三层，优先级从低到高：

1. **估算**：`ChatGeometry.defaultEstimates`（user 96 / ai 320 / 分支头 88 / 错误 160），
   带图片的条目再加 `imageExtraHeight`；
2. **持久化**：`chat_heights` 表，主键是 `(book_uuid, item_key, width_bucket, type_scale_bucket)`
   —— **同档才复用**。列宽 16dp 一档、字号 5% 一档（`ChatHeightBucket`）；
3. **本会话实测**：行布局后由 `ChatRowMeasure`（渲染对象自己）帧末上报，覆盖上面两层。

另外页面还留一份 `_heightMemo`（本页量过的高度，跨几何重建保留）：代次切换会让后面的轮次
整段移出 / 移回活动链，`dumpMeasuredHeights` 在移出那一趟就把它们弄丢了，切回来只剩估算值
（ai 320 / user 96，和真实高度差几倍），按书坐标算滚动补偿会偏出很远。换书 / 换列宽档 /
换字号档时清空——跨档高度一律不可复用。

只有**高度**进账本，**偏移**从不缓存：懒加载列表在范围估算变化后会把已构建子项整体
重排，历史偏移会失效（实测读到过 `-18288` 这种负数）。

写回是 800ms 防抖批量 upsert；`dispose` 时补一次 flush。删书要 `clearHeights`。

## 纵向留白为什么必须挂在"最后一行"上

两段留白，两套做法，都有硬理由：

| 留白 | 放在哪 | 为什么不能放 `ListView.padding` |
| --- | --- | --- |
| 顶部 24dp | `trailingSpacer` **条目**（进几何） | 放 padding 会被算进列表内容高度：跳到第 1 轮时永远差 24px（实测偏差 24 → 0） |
| 底部避开输入面板（面板高 + 8） | **最后一行**的底部内边距 | 放 padding 时它不在任何被测量的条目里，阅读锚点看不见它 —— 面板长高时**任何**滚动位置都整屏上移，位移恰好等于面板增高量（实测 92px） |

挂在最后一行之后：留白在 `ReadingAnchorItem` 的测量子树里，锚点的"贴底不补、离底补"
两条规则原样生效（离底阅读时面板长高不再推动已读内容，贴底时内容照旧被顶上去）。
`ChatRowMeasure` 包在 `Padding` **里面**，所以上报的只有内容高度，几何与持久化缓存
不会把这段留白算进去。

## 代次切换：视图停在控件，而不是停在新的底部

切代次会改写**整条活动链**：从「链尾那代」切回「有后续轮的代」，后面的轮次会随父代回来。
`reverse` 下这些新内容插在**偏移 0 那一端**，贴底时 `pixels` 保持 0 —— 视图于是落到新链的
最底部，代次控件 `← x/y →` 被顶出几屏。更麻烦的是：那一刻控件往往已经不在构建范围
（`cacheExtent` 250px）里，`localToGlobal` 根本量不到它。

所以补偿分两步，都按**书坐标**（`ChatGeometry` 偏移 + `windowBookOffsetBase`）算：

1. **布局阶段**（新链落地那一帧的 build）：算
   `Δ = 该轮 AI 行底边偏移的变化 + 窗口基准的变化`，交给 `ScrollLockAnchor` 在**同一帧布局**
   补进 `pixels`。本帧重排即生效，不会先闪一帧「新的最底部」；同时压掉阅读锚定对同一次
   内容变化的重复补偿（见上面「纵向留白」一节的锚定规则）。帧末若请求还没被取走就
   `discard`，免得漏到以后某次布局。
2. **帧末精修**（最多 8 帧）：量得到控件就直接锁它的全局 y（最准）；量不到就用书坐标
   反推目标偏移（几何会随行实测逐帧收敛）。下方内容变少到补不动时钳在列表端点，是物理上限。

锚点选 **AI 行底边**而不是行顶：控件在气泡 footer 里贴着气泡底边，正文变长变短它都不动，
只有它**后面**（更新一侧）的轮次增减 / 长高才会改变它。行顶会随正文高度一起变，不能当锚。
贴底时阅读锚定本来就不补偿（新内容该把旧内容顶上去）；而切换这一下要的是「控件原地不动」，
两者互斥，所以切换那一帧显式压掉锚定增长。

## 定位器的两条反直觉规则

1. **拖动是速度输入，不是位置输入**。手指位移换算成速度（死区 + 曲线），内容真的在滚；
   滑块只反馈"推了多远"，松手弹回中央。做成位置映射的话，手指一动内容就得跳，
   而且遇上一窗内容的 extent 变化就会撒谎。
2. **「底部」≠「最后一轮」**。底部是最大偏移；最后一轮可能只露出半屏。
   同理「第一轮的上一轮」= 顶部，「最后一轮的下一轮」= 底部。

速度模型：`Δ = clamp(滑块位移 / 120dp, ±1)`，死区 6dp，`s = sign(Δ)×|Δ|^1.3`，
`v = s × 1.6`（视口/秒）。松手立即停，无惯性。

## 跳转怎么保证准

1. 目标就近向下取整到"实际存在的轮"（轮号有断裂也能跳）；
2. 让页面准备**目标首行窗口**：非最新轮以目标为第一行、其后留两页；最新轮仍用
   贴尾窗口，避免最新轮较短时上方历史被裁空。即便目标已在旧窗口内也重新准备，
   不能沿用可能把未构建行估算进落点的旧基准；
3. 按上面的公式算落点 `jumpTo`；
4. 帧末复核：每帧重算一次落点，最多 10 帧。**必须给够 4 帧才判稳定** ——
   懒加载列表跳到新位置后才逐帧把附近的行建出来并回填实测高度（估算常差几倍），
   目标下方条目的高度一变，落点就变；"落点被可滚动上限夹住"也算没定稿。
   复核期间**暂停向上扩窗**（目标必须留在窗口第一行），向下扩窗保留。
   用户一旦开始滚动就取消复核（`cancelPendingJump`）。

## 一次构建的顺序（`_buildChatArea`）

1. `chainChanged`：书或分支变了 → `_chatWindow.reset()` + 几何重建；
2. `roundsReady`：链不属于当前书（换书异步加载的首帧）→ 一层轮次都不建；
3. 失效判据（轮次引用/长度、警告、代次、生成中气泡、列宽）→ `_rebuildGeometry`；
4. `_syncChatRows()`：把几何切成这一窗的渲染行，并算出 `windowBase`；
5. `_applyVersionAnchor()`：有代次切换锚点就按书坐标算补偿，登记给**本帧布局**
   （`ScrollLockAnchor`，见「代次切换」一节）；
6. 列表：`reverse: true` + 稳定 Key（`chat-item-${roundUuid}:${kind}`）+ `findChildIndexCallback`
   → 末尾追加时元素（连同折叠状态、选区）跟着搬家；
7. 每行包 `ChatRowMeasure`（上报高度）→ `ReadingAnchorItem`（阅读位置补偿）；
8. 轨道：只拿到 `ChatLocator`，数字全向它要。

## 踩过的坑（都留了回归用例）

1. **`visibleFraction` 写成反比**（`总高/视口`）：所有超过一屏的书都被 clamp 成 1.0，
   轨道于是**对所有正常书隐藏**，只有"几何空掉"的那本才会显示出来。
2. **窗口倒置**：链变短（换书 / 切分支）时旧实现只把 `lastRoundIndex` 夹回新总数，
   `firstRoundIndex` 不动 → `(91..10)` 这种窗口 → 一层轮次都查不到 → 整页空白。
   现在"装不下就按尾部重建"。
3. **换书首帧拿旧书轮次**：全局 provider 不随页面销毁，新页面首帧读到的可能还是上一本书的
   活动链。`loadRounds` 换书时先清链并通知，页面再用 `loadedBookUuid` 判一次。
4. **条目 Key 用轮号**：切分支后同轮号的元素被复用，会串上一分支的折叠/选中状态。
   现在一律用轮 uuid。
5. **精确边界上的"当前轮"**：视口顶正好落在某条目顶边时，`indexAt` 会给上方那一条；
   `roundIndexAtOffset` 补了这次边界修正。
6. **轨道命中带吃按钮**：轨道贴在聊天区右缘，内容区不居中时最右那枚方形按钮正好压在
   命中带里（触控端整个按钮右半都点不到）。面板按钮行按 `ChatRail.reservedFromRight` 让开。
7. **重新生成时待定气泡用了「链尾 +1」**：R2 会在发请求前先删该轮起的投影行，`nextRoundIndex`
   恰好等于目标轮号，界面自然正确；R3 改成同轮新增一代后删除没有了，界面却继续读
   `nextRoundIndex`，于是刷新第 64 轮会先显示「第 65 轮正在生成」，点停止才并回第 64 轮。
   现在由 `pendingRoundIndex` 定位、生成期间按目标轮截断视图（回归：`test/chat_pending_round_test.dart`）。
8. **代次切换只按控件实位补偿**：切回「有后续轮的代」时，整段后续轮插在偏移 0 那一端，
   控件被推出 `cacheExtent`，`localToGlobal` 量不到 → 补偿静默放弃 → 视图停在新链的最底部
   （「一切代就跳到底」）。现在先按书坐标在布局阶段补，再帧末用控件实位精修，控件量不到时
   还能用几何兜底（回归：`test/chat_round_version_test.dart` 的 UI-4）。

## 明确没做的（想清楚再动）

- **内容分页**：`RoundRepository.loadChain` 仍一次带回整条活动链，这里的"窗口"是
  **渲染窗口**，不是数据窗口。接口已按规格留好，将来做数据分页时页面零改动。
- **窗口裁剪**：数据层本就全量在内存，裁剪只对未来的分页有价值。`ChatWindowController`
  只增不减（`maxRounds` 只在"新轮把窗口撑爆"时从远端收缩）。
- **分支「上次阅读位置」记忆**：切分支统一回底部。
- **阅读位置补偿的 API 位置**：规格里叫 `correctBy(Δ)`，实际由 `ReadingAnchor` /
  `ScrollLockAnchor`（`lib/widgets/reading_anchor.dart`）承担，有一组隔离用例守着；
  不再在定位层另造一套。
- **键盘**：靠 `Scaffold` 的 `resizeToAvoidBottomInset` 把整个对话区压短（面板随之整体上移），
  不做额外的视口补偿 —— 规格 §8.8 要的正是"只挤组件"。
