## 1. 症状 → 根因 → 现状

| 症状 | 根因 | 现状 |
|---|---|---|
| 发一轮就要卡一下，甚至发送本身变慢 | 捕获路径上 `extractRawImages` 对 1.87 MB base64 跑正则回溯 | ✅ 改「`lastIndexOf` 找最近 data URL + 长度校验」，**5880 ms → 常数级**；`buildBody` 全程 **8889 ms → 197 ms** |
| 打开对话框后展开大块就卡 | 每次 rebuild 都把整块 base64 文本重跑「折叠 + 转译」两遍全量扫描 | ✅ 派生结果按「对象身份 + 返回侧字段值」缓存（`_RawBlockSnapshot`），rebuild 只读缓存 |
| 边打字边卡（输入框卡到不能用） | 每个按键都扫一遍全部块 | ✅ 检索改**手动触发**（点「搜索」/回车），扫描 **54 ms** 一次 |
| 挪一次「下一处」卡 0.5 s | 高亮加粗换字形 → 整块重排；且整块只有一份版面 | ✅ 只换底色 + 换渲染容器 + 按 2 万字符分段，见 §2/§3 |
| 移动端展开一块 >1 s | `SelectableText.rich` 内层是 `RenderEditable`，排版比 `RenderParagraph` 贵一倍且无法分摊 | ✅ 首次展开 **2353 → 472 ms（5.0x）**，每次下一处 **549–640 → 204–241 ms（2.8x）** |

## 2. 落地清单（本轮逐条）

### ① 捕获路径不再扫全文
- 改动：[raw_dialog.dart](../lib/widgets/raw_dialog.dart) 的 `extractRawImages`（正则 → `lastIndexOf` 双向定位 + 长度校验）、`expandEscapes`（一次性 `replaceAll`）。
- 实测：1.87 MB base64 的提取 **5880 ms → 探针超时（>10 s 的那格没了）**；187503 字符的转译 **127 ms → 10 ms**；一轮发送的 `buildBody` **8889 ms → 197 ms**。

### ② 派生块缓存（折叠 + 转译只算一次）
- 改动：`_RawBlock` / `_RawBlockSnapshot`（身份 + 返回侧字段值副本作 key），`_blocks` 只在派生结果失效时重算。
- 效果：反复展开 / 折叠 / 检索不再重复付全量扫描的钱；交换回填（`content` 后填）仍能正确失效（`raw_dialog_test` 有专测）。

### ③ 检索改手动触发 + 只展开当前块
- 改动：搜索框 + `raw_search_button`（回车等价）；命中表 `_matches`，`_searchBlock` 记「被检索展开的那一块」，与手点展开互不干扰。
- 实测：187503 字符 / 12500 处命中扫描 **54 ms**；打字不触发任何扫描（`raw_dialog_test` 有专测）。

### ④ 高亮只换底色，绝不动字重
- 实测（20 万字符 / 12500 处命中）：全部加粗 **0.7 s → 12 s**；只给「当前定位」加粗 **0.55 s → 2.6 s**（它随定位挪动，每点一次都要整块重排）。底色 / 前景色不换字形，交替出现几乎不要钱。
- 「当前定位」用橙色底区分（`0xFFFFB74D` α0.6），命中用黄色底（`0xFFFFF176` α0.5）。

### ⑤ 渲染容器换掉 + 按硬换行分段（本轮主刀）
- 改动：`_HighlightText` 由 `SelectableText.rich` → `SelectionArea` + 每段一个 `RichText`；分段函数 `splitAtNewlines`（预算 **20000** 字符）；补偿容器 `_TrimLine` / `_RenderTrimLine`；滚动定位 `_paragraphsOf` + `_segmentAt`（原来只找一个 `RenderEditable`，现在按字符数找到命中所在的那段）。
- 为什么换容器：同一块 20 万字符 / 25001 个 span 冷排版，`RenderEditable` **2239 ms** vs `RenderParagraph` **1123 ms**（10 段时 **1071 → 557 ms**）——`SelectableText` 那条路先天贵一倍。
- 为什么分段：整块只有一份版面，挪一次「当前定位」要重排 20 万字符（**545 ms**）；切 10 段后只重排命中所在那段（**86 ms**），5 千段 75 ms、2 千段 66 ms —— 再切细收益递减，且每段都要一层合成层，故取 **2 万**。
- 段预算实测（20 万字符 / 12500 命中，挪一次当前项）：整块 545 / 2 万 86 / 5 千 75 / 2 千 66 ms。

## 4. 分段不能破坏的东西（全部实测过）

- **段尾那个空行**：引擎把「最后一个换行之后」也算一行 → `a` = 19.00 px、`a\n` = 38.00 px。19 段共多 18 行（4161 vs 3819）。所以切点必须落在 `\n` **之后**（各段拼回逐字相同，跨段复制才不会丢分隔符），多出来的空行用 `_TrimLine` 从各段容器 size 里裁掉。裁完总高 **3819.00 = 整块 3819.00**，逐字 dx/dy **0.00 px**。
- **补偿量必须实测行高**：名义 `fontSize × height` = 12.5 × 1.5 = 18.75，引擎按物理像素吸成 **19.00**（dpr 3）。用 `TextPainter` 量一个字拿到 19.000，与 Widget 量到的段尾空行**等高**；拿名义值会让每个接缝差 0.25 px。
- **命中定位**：`_segmentAt` 按各段字符数累加找到命中所在段，再 `getOffsetForCaret` 取行顶 —— 不再为定位另起 `TextPainter` 排一遍整块（那在数百 KB 上单次 >200 ms）。
- **跨段选中复制**：拖动跨段 + 反向拖动，复制结果与整块**逐字相同**（`raw_dialog_test` 有专测；`test/helpers/raw_dialog_harness.dart` 提供分段块的坐标 / 文本读取脚手架）。

## 5. 死路清单（别再试）

| 想法 | 实测结果 |
|---|---|
| 改 `\n` 自身样式压空行（字号 0.01 / 行高 0 / 两者叠加） | 四种全废，`a\n` 恒 **38.00** |
| 改段落根 span 的默认样式压空行 | 一样压不掉：`a\n` 仍 38.00、`x\ny\n` 仍 57.00（三行），合成单子 span 也 38.00 |
| `maxLines` 吃掉段尾空行 | 它数**视觉行**：首段 209.00 → 限行后 **19.00**，折行内容被截没。RAW 长行遍地，不可用 |
| 负 `Padding(top:)` / 负 `Column(spacing:)` | 都被框架断言拦住：`shifted_box.dart:134 'padding.isNonNegative'`、`RenderFlex` 要求 `spacing >= 0` |
| `heightFactor` 压掉一行 | 只收非负值（`_RenderLimitedBox` 断言 `0 <= heightFactor`），且乘的是**传入约束**，压不动子节点高度 |
| `CustomMultiChildLayout` 画到负偏移 | 能画，但源码明说自己的 size 不许依赖子节点 → 还得自定义 render object，不如直接写 |
| 换行不留 / 归下一段开头 | 版面与复制只能保一头：丢了复制出的 JSON 挤成一行，归下段照样多一行 |
| 每 2000 字符切段 | 只比 2 万多省 20 ms，段数与合成层翻 10 倍，不值 |

## 7. 遗留可选项（未做）

- **每段独立滚动可见性**：现在 10 段都在同一个 `SingleChildScrollView` 里，屏幕外的段照样参与绘制录制。真要再省，可给每段包 `RepaintBoundary` 或在滚动时跳过屏幕外段的 span 重建 —— 但当前 472 ms 的首帧已够用，收益不如风险大。
- **挪当前项仍重建整块的 span 序列**：`_HighlightText` 每次 build 会对全部段跑 `countMatches` + `highlightSpans`（20 万字符的分配）。这是剩下 204 ms 的主要来源；缓存各段 span、只重建失去 / 获得橙底的两段，可望再降到 ~80 ms。属增量优化，未在本轮动。
- **段预算随平台变**：Android 上 dpr 更高、单段更长会更贵；若真机反馈仍卡，把 `_segmentBudget` 提到 1 万即可（实测 5 千段只比 2 万多省 11 ms，方向上是安全的）。
